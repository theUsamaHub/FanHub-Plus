## 1. Executive summary

Three areas were audited. One design is sound, one is a misdiagnosis worth correcting, and one is a real architectural problem.

| Area | Verdict |
|---|---|
| **Media** | Design is **correct and worth keeping**. Central library, entities point at it, blades never touch `Storage`. But the migration from the old polymorphic design is only ~60% complete — no shared trait, inconsistent validation, one unguarded delete path. **Deferred by decision.** |
| **Ratings vs Reviews** | **Not duplicates.** They answer different questions and have different cardinality. The real defect is that **neither has a public write path**, so `reviews`' fully-built moderation queue can never fill in production. **Left alone by decision.** |
| **Upcoming** | **Real problem.** "Upcoming" is implemented **four separate times** across four tables using **two incompatible mechanisms**. `upcoming_releases` is a redundant 4th implementation. **Decision: drop it, consolidate onto `contents`.** |

### The single most important finding

`HomepageService` builds the Upcoming page by `UNION ALL`-ing **three tables with three different date semantics** into one raw query:

```
app/Services/HomepageService.php:117-165
  Content           → whereDate('release_date', '>=', today())     [computed]
  UpcomingRelease   → whereNull(release_date) OR >= today()        [computed, different]
  MerchandiseItem   → where('is_upcoming', true)                   [stored boolean]
```

`merchandise_items` is filtered by **both** a stored boolean and a date comparison, and nothing in the codebase ever writes one from the other — so they can disagree, and an item can be silently dropped from the page. See [§5.4](#54-the-merchandise-double-filter-bug).

## 2. Decisions taken

| # | Question | Decision |
|---|---|---|
| 1 | How is "is upcoming" determined? | **Computed from `release_date`, no new boolean column.** Single source of truth. |
| 2 | How far does the date rule extend? | **Consolidate onto `contents`.** Do not create a dedicated upcoming table. |
| 3 | Media issues? | **Leave media alone this round.** |
| 4 | Ratings / reviews? | **Leave alone this round.** |
| 5 | When to implement? | **Not now.** This document is the deliverable. |

### Rejected alternatives, and why

- **Adding an `is_upcoming` boolean to `upcoming_releases`** (mirroring `merchandise_items`) — rejected. It creates two sources of truth that drift. A computed accessor has no drift and needs no cron job, because dates pass without any row being touched.
- **Keeping `upcoming_releases` as a dedicated table** — rejected. It duplicates `contents` on 5 of 8 columns and adds a 3rd source to an already 3-way union.
- **Forcing a boolean with a scheduled recompute job** — rejected. More machinery for no benefit over a computed accessor.

## 3. Audit A — Media library

### 3.1 What is correct

The instinct to have a standalone media library is right, and the implementation is largely good.

**The media table is genuinely standalone.** Migration `2026_09_23_000001_restructure_media_table.php` removed the old polymorphic back-reference:

| Dropped | Why it was right to drop it |
|---|---|
| `mediable_type`, `mediable_id` | A file could only ever belong to one parent. A shared library cannot express "this image is used by 3 categories". |
| `name` | Ambiguous with `original_filename`. |
| `original_name` | Superseded by `original_filename`. |
| `size` | Renamed to `size_bytes` for unit clarity. |
| `created_by` | Renamed to `uploaded_by` for actor clarity. |

**Final `media` columns** (after all migrations in order):

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | bigIncrements PK | no | |
| `uploaded_by` | FK → `users.id` | yes | `ON DELETE SET NULL` |
| `mime_type` | varchar(100) | **yes** | |
| `media_type` | enum(`image`,`video`,`audio`,`document`) | no | `image` |
| `size_bytes` | unsignedBigInteger | yes | |
| `width` | unsignedInteger | yes | |
| `height` | unsignedInteger | yes | |
| `duration` | decimal(10,2) | yes | seconds |
| `alt_text` | varchar(255) | yes | |
| `path` | varchar(500) | no | disk-relative key |
| `original_filename` | varchar(255) | yes | |
| `disk` | varchar(50) | no | `public` |
| `created_at` / `updated_at` | timestamp | yes | |

Surviving indexes: `idx_media_type`, `media_mime_type_index`, `(mime_type, created_at)`.

**Ownership is expressed correctly by the referencing side** — 6 scalar FKs + 2 pivots, all `nullOnDelete` or `cascadeOnDelete`:

| Referencing column | → | Pivot? | Migration |
|---|---|---|---|
| `categories.icon_media_id` | `media.id` | scalar | `2026_09_23_000002:13` |
| `user_profiles.avatar_media_id` | `media.id` | scalar | `2026_09_23_000003:14` |
| `character_profiles.image_media_id` | `media.id` | scalar | `2026_09_23_000007:17` |
| `merchandise_items.image_media_id` | `media.id` | scalar | `2026_09_23_000008:17` |
| `events.cover_media_id` | `media.id` | scalar | `2026_09_23_000009:24` |
| `content_media.media_id` | `media.id` | pivot, `role` enum | `2026_09_23_000006:14` |
| `event_media.media_id` | `media.id` | pivot, no role | `2026_09_25_000001:33` |

**Blades never touch `Storage`.** Every image URL is produced by a model accessor, so disk logic lives in exactly one place. This is good and should be preserved.

### 3.2 Findings

#### M-1 — No `HasMedia` trait exists · **Medium**

`CONTEXT.md` documents a `HasMedia` trait with `media()`, `addMedia()`, `addMediaFromRequest()`, `getFirstMedia()`, `getImages()`, `clearMedia()`, `removeMedia()`. **None of it exists.** `app/Traits/` contains only `HasAuditColumns`, `HasRoles`, `HasSlug`, `HasTags`, `LogsActivity`.

A project-wide search for `HasMedia`, `addMediaFromRequest`, `getFirstMedia`, `clearMedia`, `removeMedia`, `getImages` returns **zero matches**.

Four ad-hoc attach patterns have replaced it:

| Pattern | Where | Problem |
|---|---|---|
| Scalar FK set directly | 5 models | No shared helper, no cleanup on detach |
| `delete-all-then-recreate` pivot | `app/Services/ContentService.php:131-146` | Non-atomic; blows away `sort_order` on every save |
| `belongsToMany()->sync()` | `app/Http/Controllers/Admin/EventController.php:60,84` | Fine, but inconsistent with the above |
| Upload-and-point | `Admin/CategoryController.php:48,94`, `ProfileController.php:45-51` | Hardcodes its own directory, bypasses the picker UI |

**Impact:** No model has a `detach`, `clear`, or cascade helper. Orphan cleanup happens in exactly two hand-written places.

#### M-2 — `referenceCount()` misses `upcoming_releases` · **Medium**

`app/Models/Media.php:126-135` counts 7 reference sites. `upcoming_releases.image_media_id` is **not among them**.

**Impact:** an image used *only* by an upcoming release reports `isReferenced() === false`, so the admin delete button stays enabled at `resources/views/admin/media/index.blade.php:117,129`. Not data loss — the FK is `nullOnDelete` so the column is nulled — but the guard lies to the admin.

**Note:** this finding becomes moot if `upcoming_releases` is dropped per [§6](#6-plan--consolidate-upcoming-onto-contents).

#### M-3 — API deletes shared media with no guard · **High (real bug)**

Two code paths replace a category icon:

```
Admin/CategoryController.php:104-109     → guarded by isReferenced()   ✅
Api/V1/CategoryController.php:73-75      → NOT guarded                 ❌
```

**Impact:** if two categories share an icon, an update through the **API** destroys the file and the `media` row outright, then `nullOnDelete` silently nulls the *other* category's `icon_media_id`. That category loses its icon with no error and no log. The web path correctly refuses.

#### M-4 — Media type validation is inconsistent · **Medium**

`EventRequest.php:26` constrains the cover to an image:

```php
'cover_media_id' => [..., Rule::exists('media','id')->where('media_type','image')]
```

`ContentRequest.php:39-45` applies **no** `media_type` constraint to `cover_media_id`, `trailer_media_id`, or `audio_clip_media_id`.

**Impact:** a video can be saved as a content cover. And the accessor does not catch it either — `Content::getArtworkUrlAttribute()` (`app/Models/Content.php:87-90`) returns `$this->cover?->url` with **no `isImage()` check**, while `Event.php:75` and `CharacterProfile.php:33` both *do* check. So a video cover renders as a broken `<img>`.

#### M-5 — Parallel image system in `settings` · **Low**

`database/seeders/SettingsSeeder.php:16,17,23` seeds three settings as `type => 'image'` with a **raw string value and no media FK**:

- `general.site_logo`
- `general.site_favicon`
- `seo.og_image`

The admin settings UI offers `image` as a type option (`admin/settings/index.blade.php:156`) but **no blade view reads any of these three keys** — zero matches across `resources/views`. They are ungoverned raw-string fields that would store a path outside the library if filled in.

#### M-6 — Config-driven fallback images bypass the library · **Low**

`config/homepage.php:5-26` hardcodes ~19 image paths under `images/`, served via `asset()` straight from `public/images/`, never entering the `media` table. Consumed by the homepage hero, characters, trending, and every `artwork_url` fallback.

Separately, `resources/views/events/index.blade.php:10` inlines a literal path that is **not** in the config:

```blade
style="--events-hero-image: url('{{ asset('images/hero/photo-1667419674923-9eef9f86c628.avif') }}')"
```

This is a static-asset concern rather than a bug, but it means the library has no single fallback source.

#### M-7 — `MediaSeeder` seeds rows pointing at files that don't exist · **Medium**

`database/seeders/MediaSeeder.php:16-25` inserts 10 rows with `path` values like `media/hero_banner.jpg` and `disk => 'public'` — i.e. `public/storage/media/hero_banner.jpg`. On disk, `public/storage/uploads/` contains only `categories/`, and `storage/app/public/` is empty.

`Media::getUrlAttribute()` (`app/Models/Media.php:47-54`) only checks the path is non-empty — it never calls `Storage::exists()`.

**Impact:** downstream seeders point entities at these phantom rows (`EventSeeder.php:15,45`, `CharacterProfileSeeder.php:16,41`, `MerchandiseItemSeeder.php:16,41`, `UserProfileSeeder.php:15,21`, `ContentMediaSeeder.php:15,31`), so a freshly seeded database renders **broken images on the homepage**.

#### M-8 — `content_media.role = 'attachment'` is stored but never rendered · **Low**

Validated (`ContentRequest.php:44-45`) and synced (`Admin/ContentController.php:151`), but `resources/views/public/content.blade.php` only iterates `gallery`, `trailer`, and `audio_clip` (lines 18–20). Uploads are accepted, stored, and never shown.

#### M-9 — Dead `MediaController` stub · **Low**

`app/Http/Controllers/MediaController.php` — all 7 methods have empty bodies (`:13-64`). Not routed anywhere. The live controller is `Admin/MediaController.php` (138 lines).

#### M-10 — Inconsistent upload UX · **Low**

Two entities still do direct file uploads into their own folders; five are library-picker-only.

| Entity | Mechanism | Directory |
|---|---|---|
| Category icon | direct upload | `uploads/categories` |
| User avatar | direct upload | `uploads/avatars` |
| Content, Event, Character, Merchandise, UpcomingRelease | **picker only** | `uploads/{images,videos,audio,documents,spreadsheets}` |

Direct uploads still create a proper `media` row, so nothing is orphaned — but the admin experience and the validation applied are different between the two groups.

## 4. Audit B — Ratings vs Reviews

### 4.1 These are not duplicates

The original question was *"why does both exist?"* They are **not** redundant. They model different things:

| | `ratings` | `reviews` |
|---|---|---|
| Question | "How good is it?" | "What do people say?" |
| Payload | 1 integer (`stars`) + 1 boolean (`is_thumbs_up`) | `title` + `body` text |
| **Per user per target** | **exactly 1** — enforced by `uq_rating_unique` | **many** — no constraint |
| Moderation | **none** — no `status` column | `pending` → `approved` / `rejected` |
| Intended surface | a 4.5★ number on a card | a wall of written opinions |
| Polymorphic columns | `rateable_type` / `rateable_id` | `reviewable_type` / `reviewable_id` |

A single star rating and a paragraph review are genuinely different data. **Merging them would be wrong.** The right relationship is: a review *may* accompany a rating.

### 4.2 The actual defect: no public write path

**Nothing in the entire application ever creates a `Rating` or a `Review`.** There is no `store()` method on either controller, no form request, no public route, no public view, no API endpoint. Rows only ever come from `RatingSeeder`, `ReviewSeeder`, and tests.

| Surface | `ratings` | `reviews` |
|---|---|---|
| Public UI | **absent** | **absent** |
| API | **absent** | **absent** |
| Admin UI | read + delete list only | full moderation |

So `reviews` has a **completely built moderation pipeline that can never fill**:

- `ReviewController` — index, show, approve, reject, destroy
- Dashboard tile "Pending Reviews" → `admin/dashboard.blade.php:145-155`
- Dashboard chart "Reviews by status" → `admin/dashboard.blade.php:315-318`, `admin-dashboard.js:249`
- Analytics "Review moderation volume" → `analytics/index.blade.php:121-137`
- `DashboardInsightService.php:152` ops-throughput insight
- User detail "Recent reviews" → `admin/users/show.blade.php:134-153`

All of it renders `0` forever.

And `ReviewSeeder.php:47` hardcodes all 10 seeded reviews as `status => 'approved'`, so even the seeded DB shows an empty queue.

### 4.3 Dead code

| Finding | Location |
|---|---|
| **The two models are coupled.** `Rating::getTargetLabelAttribute()` calls `Review::friendlyTargetLabel()`. Neither can be removed without breaking the other. | `app/Models/Rating.php:40` |
| Unused import — `Rating` imported, never referenced in the file. | `Admin/AnalyticsController.php:10` |
| Eager-loaded but never rendered — `$user->ratings` loaded, no "Recent ratings" table in the view (unlike reviews at `:134`). | `Admin/UserController.php:63` |
| Three dead scopes — `scopePending/Approved/Rejected` never called; 6 sites inline the same `->where('status','pending')`. | `app/Models/Review.php:31-44` |
| Dead relation — `Content::reviews()` is never used in any controller, view, or test. | `app/Models/Content.php:72-75` |
| **No model has a `ratings()` relation at all.** Not one. | — |
| **No `app/Policies/` directory.** Both tables are gated by route middleware only, not per-record authorization. | — |
| `Review` has **no `casts()`** method at all, unlike every other model. | `app/Models/Review.php` |

### 4.4 Coverage gap

`Review::friendlyTargetLabel()` (`:51-68`) maps four target types — `Content`, `MerchandiseItem`, `CharacterProfile`, `Event` — but:

- **Only `Content` has a `reviews()` relation.** `CharacterProfile`, `MerchandiseItem`, and `Event` have **no** relation to either table.
- **Only `Content::class` is ever written** as a polymorphic type — in `ReviewSeeder.php:41`, `RatingSeeder.php:29`, and three test files.

So the label helper advertises four supported targets; the schema and seeders support one.

### 4.5 Summary

**Verdict: keep both tables. The design is right; the implementation is a pair of half-built features.**

The missing piece is a **public write path** — a "☆ rate this" and "write a review" flow on content/character/merchandise/event pages, with `reviews` entering `pending` for moderation and `ratings` writing straight through. Until that exists, both are dead weight and both admin screens are theatre.

**Deferred by decision.** Recorded here so it is not lost.

## 5. Audit C — Upcoming releases

### 5.1 The concept is implemented four times

| # | Source | Table | `is_upcoming`? | "Is upcoming" test | `release_label`? | Public detail page? | `kind`? |
|---|---|---|---|---|---|---|---|
| 1 | Content | `contents` | ❌ | `whereDate('release_date','>=',today())` | ✅ | `/stories/{slug}` | ❌ |
| 2 | Merchandise | `merchandise_items` | ✅ **boolean, indexed** | `where('is_upcoming',true)` | ❌ (uses `tag`) | `/collection/{slug}` | ❌ |
| 3 | Event | `events` | ❌ | `starts_at`, separate route | ❌ | `/events/{slug}` | ❌ |
| 4 | UpcomingRelease | `upcoming_releases` | ❌ | `whereNull(release_date) OR >= today()` | ✅ | `/releases/{slug}` | ✅ 6 kinds |

**Two incompatible mechanisms:** a stored boolean (`merchandise_items.is_upcoming`, default `false`, indexed `idx_merch_upcoming`) versus a computed date filter (the other three).

**Nothing in the codebase ever writes `is_upcoming` from `release_date`.** Confirmed: the only appearance of `is_upcoming` in any migration is the `merchandise_items` create (`:18`) and its index (`:20`). No controller, service, seeder, or command derives it.

### 5.2 The homepage unions three of them

`app/Services/HomepageService.php` has two parallel implementations of the same feed:

**`releases()` (`:55-100`)** — three separate Eloquent queries, mapped to arrays, then `concat()`-ed in PHP:

```php
$contents->concat($upcoming)->concat($merchandise)
    ->sortBy(fn ($item) => $item['date']?->format('Y-m-d') ?? '9999-12-31')
    ->take($limit)->values();
```

**`paginatedReleases()` (`:117-165`)** — the same three sources as raw `UNION ALL` branches with `selectRaw`, wrapped in `DB::query()->fromSub(...)`, then **three follow-up queries** to re-resolve artwork by kind:

```php
DB::query()->fromSub(
    $content->toBase()->unionAll($upcoming->toBase())->unionAll($merchandise->toBase()),
    'releases'
)->orderByRaw('CASE WHEN release_date IS NULL THEN 1 ELSE 0 END')
  ->orderBy('release_date')->orderBy('kind')->orderBy('id')
  ->paginate(12)->withQueryString();
```

These two implementations can disagree, and neither is unit-tested against the other.

### 5.3 `upcoming_releases` is a redundant 4th implementation

`upcoming_releases` duplicates `contents` on **5 of 8** data columns:

| `upcoming_releases` | `contents` | Identical? |
|---|---|---|
| `title` varchar(200) | `title` varchar(255) | ~ |
| `slug` varchar(220) unique | `slug` varchar(280) unique | ~ |
| `category_id` | `category_id` | **differs** — nullable/`nullOnDelete` vs required/`restrictOnDelete` |
| `release_date` date nullable | `release_date` date nullable | ✅ **identical** |
| `release_label` varchar(60) | `release_label` varchar(60) | ✅ **identical** |
| `kind` varchar(40) | — | ❌ **no equivalent** |
| `description` text | `excerpt` varchar(500) / `body` longtext | partial |
| `image_media_id` | `content_media` pivot `role='cover'` | ✅ equivalent via library |
| `is_published` boolean | `status` enum + `published_at` | different mechanism |
| `sort_order` | — | ❌ **no equivalent** |
| `idx_upcoming_pub_date` (`is_published`,`release_date`) | — | ❌ **no `release_date` index on `contents`** |

`contents` **already** has `release_date` and `release_label`, both validated in `ContentRequest.php:22-23`, both rendered in `admin/contents/partials/form.blade.php:36-43`, and both already fed into the homepage union at `HomepageService.php:57`.

**Conclusion: the table adds a 3rd branch to an already 3-branch union, in order to serve a page that `contents` could serve.**

### 5.4 The merchandise double-filter bug

`MerchandiseItem::scopeUpcoming()` (`app/Models/MerchandiseItem.php:58-61`) filters `where('is_upcoming', true)`.

`HomepageService` then applies a **second, independent** date filter on the same query:

```php
HomepageService.php:100
->where(fn ($query) => $query->whereNull('release_date')->orWhereDate('release_date', '>=', today()))
```

A merch item with `is_upcoming = false` and a **future** `release_date` satisfies the date test but is excluded by the scope. A merch item with `is_upcoming = true` and a **past** `release_date` satisfies the scope but is excluded by the date test. Because nothing syncs the boolean to the date, both states are reachable and the item vanishes from the Upcoming page with no admin signal.

**This is the same class of bug the `upcoming_releases` admin has** — see [§5.5](#55-the-admin-has-no-upcoming-signal).

### 5.5 The admin has no "upcoming" signal

`admin/upcoming-releases/index.blade.php` shows an **Upcoming** stat card (`:38` → `UpcomingRelease::published()->upcoming()->count()`) but the table (`:74-104`) has columns for Title, Kind, Category, Release Date, Label, Published, Actions — **and no Upcoming column**.

There is no toggle, no override, no badge. A release dated in the past silently drops off `/discover/upcoming` and `/releases/{slug}` stays reachable, with **zero indication in the admin list that this happened or why**.

### 5.6 What `upcoming_releases` has that `contents` lacks

To be fair to the table, it is not pure duplication:

| Capability | `upcoming_releases` | `contents` |
|---|---|---|
| `kind` taxonomy (anime/event/movie/series/game/merchandise) | ✅ | ❌ — `type` is `article/video/audio/image`, a **format**, not a release kind |
| `sort_order` manual ordering (TBA items sort last) | ✅ | ❌ |
| Dedicated release-framed detail template | ✅ `public/upcoming-show.blade.php` | ❌ — `public/content.blade.php` is a story template |
| Composite index for the public query | ✅ | ❌ |
| Body text | `description` | `body` longtext ✅ |

**The `kind` column is the real blocker.** See [§6.3](#63-blocker-kind-has-no-home-in-contents).

### 5.7 Migration state

```
2026_09_25_000002_remove_color_from_tags_table ......... Pending
2026_10_01_000001_create_upcoming_releases_table ........ [5] Ran
```

The `upcoming_releases` migration is **dated 6 days in the future but has already run** on the local database. Dropping the table therefore requires a **forward data migration**, not merely deleting the migration file.

## 6. Plan — Consolidate upcoming onto `contents`

**Status: NOT STARTED.** This is the agreed direction. Nothing below has been implemented.

### 6.1 Goal

One source of truth for "upcoming": `contents.release_date`, combined with `contents.status`. Remove `upcoming_releases`. Reduce the homepage union from 3 branches to 2.

### 6.2 Field mapping

| `upcoming_releases` | → `contents` | Action |
|---|---|---|
| `title` | `title` | direct |
| `slug` | `slug` | direct |
| `category_id` | `category_id` | direct; **null → must be resolved**, `contents` requires it |
| `release_date` | `release_date` | direct, **no change** |
| `release_label` | `release_label` | direct, **no change** |
| `description` | `excerpt` (500) or `body` | **needs a decision** — see [§6.4](#64-decision-description--excerpt-or-body) |
| `image_media_id` | `content_media` row, `role='cover'` | via `ContentService::syncMedia()` |
| `is_published = true` | `status = 'published'`, `published_at = now()` | map |
| `kind` | **unmapped** | **blocker** — [§6.3](#63-blocker-kind-has-no-home-in-contents) |
| `sort_order` | `is_featured`? no — **unmapped** | decide, or drop |
| — | `type` | must set to `article` (no content-format equivalent) |

### 6.3 Blocker: `kind` has no home in `contents`

`contents.type` is `enum('article','video','audio','image')` — a **content format**. `upcoming_releases.kind` is `anime|event|movie|series|game|merchandise` — a **release medium**. These are orthogonal and must not be conflated.

Three options, in order of preference:

| Option | Approach | Trade-off |
|---|---|---|
| **A** *(recommended)* | Add `kind` to `contents` as a **nullable** enum, same 6 values. `null` for ordinary content. | Clean, queryable, mirrors the existing design. One migration. No existing behaviour changes. |
| **B** | Map `kind` → `Tag`, reuse the existing `content_tags` pivot. | No schema change. But tags are a flat vocabulary shared with real content tags — "Movie" as a tag pollutes the tag list, and the Upcoming page would need a tag-based filter. |
| **C** | Drop `kind` entirely. Derive a display label from `category_id` instead. | Simplest. Loses the medium distinction — an anime and a movie in the same category become indistinguishable on the card. |

Option **A** is recommended. It makes the kind filterable, keeps the 6-value taxonomy the seeder already relies on, and a `null` kind leaves every existing content row untouched.

### 6.4 Decision: `description` → `excerpt` or `body`?

`upcoming_releases.description` is `text` and the seeder writes one-sentence blurbs (e.g. *"The epic final battle arrives on the big screen."*). `contents.excerpt` is `varchar(500)` and is already the summary field rendered on cards and in `public/content.blade.php`.

**Recommendation:** map to **`excerpt`**. `body` is the long-form article body rendered by the WYSIWYG editor; release blurbs are not article bodies, and populating `body` would make every migrated release render a full article layout.
